Enterprise AI Platform Engineering & Operations

A direct path in. Four phases to move from scattered API keys to governed, production-grade AI agents.

01

Phase 0: Assess 2–6 weeks fixed fee

Most engagements start here. We inventory the current state before committing to a build: API keys, shadow AI, traffic paths, existing MDM, EDR, NGFW, ZTNA and SWG capabilities, and the first cut of data classification.

  • Fill the traffic coverage table for every AI path in the organization.
  • Identify unmanaged provider keys, direct model access and unapproved MCP connections.
  • Deliver a regulatory exposure report covering EU AI Act, NIS2, GDPR and ISO 42001.
  • Deliver a costed technical design, layer by layer, that the customer can keep and implement with any vendor.

The assessment is a fixed-fee entry point. You can keep the design and walk away.

02

Phase 1: Foundation — The Control Plane

Deploy the platform scaffolding and route all model traffic through the gateway. By the end of this phase there are no direct provider keys in use and every change is applied through Git.

  • AI Gateway: HA LiteLLM with Rust hot path, virtual keys with cost tags, SSO, budgets and egress rules.
  • Endpoint control: MDM profiles for IDE assistants such as Claude Code and opencode, locking providers to the gateway and provisioning skills.
  • Observability: OpenTelemetry collector, LLM tracing, platform dashboards and SIEM feed.
  • FinOps: cost data pipeline with provider billing reconciliation and weekly showback per team.
  • GitOps: repositories, CI/CD pipelines and Argo CD for all platform components; no manual production changes.
03

Phase 2 & 3: Governed Tools & First Agents

Connect enterprise systems through the MCP Tool Hub and launch the first internal agent. Everything stays read-only or approval-gated until identity propagation and policy are proven.

  • MCP Tool Hub: deploy agentgateway with registry, virtual servers and per-tool CEL policies.
  • Source systems: connect code, Jira, Confluence, documents and Slack via on-behalf-of OAuth 2.1 token exchange.
  • Knowledge agent: built on LangGraph with Letta conversational profiles, answering in Slack from permission-aware sources.
  • Memory pilot: scoped memory with Mem0 and pgvector, carrying source ACLs and data tier into retrieval.
04

Phase 4: Operations Agents & Managed AIOps

Add write capability with human-in-the-loop approvals, then transition to ongoing platform operations. Cost is reported per outcome, not just per token.

  • Write variants: Jira, CRM, ERP and Argo CD write tools route through Slack Block Kit approvals with signed interactions and hash-chained audit.
  • Operations agents: SRE triage agent and CI/CD triage agent, the latter running on the opencode serve coding-agent pool to propose fix PRs.
  • Unit economics: cost per answered question, per triaged incident and per assisted PR.
  • Managed retainer: monthly platform operations covering model lifecycle governance, FinOps optimization, security updates and SLO management.
05

Decisions We Make Together

The architecture is shaped by customer choices made during assessment and foundation. These are not optional configuration details; they define the risk posture and operating model.

  • EU data residency requirement: none, EU-routed providers for Confidential, or sovereign specialist / managed EU inference for Restricted.
  • Content logging defaults: how much prompt content to log, balancing audit needs against employee privacy and works-council consultation.
  • Classification of the initial tool set: which systems are Internal, Confidential or Restricted.
  • Existing security stack integration: which MDM, EDR, NGFW, ZTNA, SWG and SIEM products receive platform-generated rules and signals.
  • Chargeback vs. showback: whether teams see cost or are actually charged back, and which allocation keys to use.
  • SaaS-only dependencies: whether to accept the official Slack and Atlassian MCP servers or use self-hosted generated API tools.
